## Решение о слиянии

**Не выполнять автоматический merge/cherry-pick альтернативного `report_pipeline.py`.**

В `AI Reset` реализован намеренно простой production backend v1:
`полная TXT-транскрипция -> 1 локальный запрос к Qwen -> проверка Markdown -> сохранение без перезаписи`.
Это соответствует `AI_REPORT_STATUS_2026-09-07.md` и `AGENTS.md`: цель продукта — практически полезный отчёт, а не формальный проверяемый протокол. Документы сообщают о 95/95 deterministic checks; в ходе текущей сверки эти тесты **не перезапускались**.

Альтернативный `report_pipeline.py` использует другую архитектуру:
- текст делится на чанки с контролем покрытия;
- извлекаются и привязываются к исходнику `EvidenceRecord`;
- отдельно обрабатываются решения и числовые факты;
- при переполнении контекста выбираются evidence ID;
- финальный отчёт строится из отобранных фактов, с несколькими LLM-вызовами.

Это потенциально полезно для доказательных отчётов, но дороже и сложнее. Продемонстрированного преимущества для принятого meeting-report v1 по имеющимся материалам нет.

### Прямая подмена несовместима

`transcriber_app.py` в `AI Reset` импортирует из `report_pipeline` функции `load_template`, `output_path_for` и тип `ReportPipelineError` и использует CLI production backend.

Альтернативный модуль предлагает другие точки входа (`load_report_template`, `run_report_with_lifecycle`, `write_new_report`), другие структуры данных и аргументы CLI. Замена одного файла без изменения GUI и тестов вызовет регрессии. Кроме того, production-тест прямо запрещает импорт старой `EvidenceRecord`-архитектуры в модуль `report_pipeline.py`.

## Что сохраняем

- Базой дальнейших улучшений считаем `AI Reset`.
- Альтернативную ветку целиком сохраняем как research checkpoint; ничего из неё не удаляем.
- Предложения из альтернативы проверяем только при доказанном существенном дефекте: выдуманные решения, задачи, исполнители, сроки, числа или потеря важной части встречи.
- При необходимости экспериментировать с evidence-based отчётом используем отдельный модуль и отдельные тесты, не заменяя production backend v1.
- `main` не обновляем до тестов и решения о выпуске.

## Следующий этап: macOS

Цель: самодостаточное macOS-приложение, без ручной установки Python и библиотек конечным пользователем. При первом запуске программа должна проверять наличие моделей Whisper и локальной модели отчётов, показывать размер загрузки и скачивать их только после согласия пользователя.

Порядок:
1. Провести Windows-регрессионный аудит актуальной ветки, зафиксировать рабочий набор тестов и упаковки.
2. Выделить платформозависимые функции: системные пути, FFmpeg, запуск subprocess, открытие папок, CPU/GPU detection, хранение пользовательских файлов и скачанных моделей.
3. Подготовить macOS runtime/package и сборку `.app` в GitHub Actions (macOS runner); не пытаться запускать Windows .exe/.cmd на Mac.
4. Включить Python, нужные библиотеки и FFmpeg в пакет (с проверкой лицензий); загружать большие модели отдельно через существующий менеджер или его адаптацию.
5. Выполнить автоматические проверки на Windows и macOS. Отдельно отметить, что CI не является заменой GUI/drag-and-drop/Whisper smoke test на реальном Mac.
6. Только после результатов тестов обсуждать подпись, notarization, распространение и Apple Silicon acceleration.

**Границы этой фиксации:** исходный код не менялся, сборки и тесты здесь не запускались. Это документированное решение по GitHub-исходникам и двум зафиксированным веткам.
